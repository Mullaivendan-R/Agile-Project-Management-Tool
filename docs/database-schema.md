## 1. Entity-Relationship Overview

## 2. Table Specifications

### 2.1 `projects` Table
Represents high-level business initiatives.

| Column | Type | Nullable | Default | Constraints & Details |
|---|---|---|---|---|
| `id` | INTEGER | No | Auto-increment | Primary Key |
| `name` | VARCHAR(255) | No | None | Indexed, min length 1 |
| `description` | TEXT | Yes | NULL | Optional project scope |
| `status` | VARCHAR(50) | No | `'PLANNING'` | Enum: `PLANNING`, `ACTIVE`, `COMPLETED`, `ARCHIVED` |
| `created_at` | DATETIME | No | CURRENT_TIMESTAMP | UTC timestamp of record creation |
| `updated_at` | DATETIME | No | CURRENT_TIMESTAMP | UTC timestamp of latest update |

### 2.2 `stories` Table
Represents agile User Stories delivering end-user capabilities within a Project.

| Column | Type | Nullable | Default | Constraints & Details |
|---|---|---|---|---|
| `id` | INTEGER | No | Auto-increment | Primary Key |
| `project_id` | INTEGER | No | None | Foreign Key &rarr; `projects(id)` ON DELETE CASCADE |
| `title` | VARCHAR(255) | No | None | Min length 1 |
| `description` | TEXT | Yes | NULL | Acceptance criteria / user story details |
| `status` | VARCHAR(50) | No | `'BACKLOG'` | Enum: `BACKLOG`, `TODO`, `IN_PROGRESS`, `DONE` |
| `priority` | VARCHAR(50) | No | `'MEDIUM'` | Enum: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `created_at` | DATETIME | No | CURRENT_TIMESTAMP | UTC timestamp |
| `updated_at` | DATETIME | No | CURRENT_TIMESTAMP | UTC timestamp |

### 2.3 `tasks` Table
Represents actionable units of engineering work required to complete a User Story.

| Column | Type | Nullable | Default | Constraints & Details |
|---|---|---|---|---|
| `id` | INTEGER | No | Auto-increment | Primary Key |
| `user_story_id` | INTEGER | No | None | Foreign Key &rarr; `stories(id)` ON DELETE CASCADE |
| `title` | VARCHAR(255) | No | None | Min length 1 |
| `description` | TEXT | Yes | NULL | Implementation details / notes |
| `status` | VARCHAR(50) | No | `'TODO'` | Enum: `TODO`, `IN_PROGRESS`, `DONE` |
| `priority` | VARCHAR(50) | No | `'MEDIUM'` | Enum: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `assigned_to` | VARCHAR(255) | Yes | NULL | Assignee handle or email |
| `due_date` | DATETIME | Yes | NULL | Target deadline for background monitor tracking |
| `created_at` | DATETIME | No | CURRENT_TIMESTAMP | UTC timestamp |
| `updated_at` | DATETIME | No | CURRENT_TIMESTAMP | UTC timestamp |

### 2.4 `notifications` Table
Stores deadline reminders and overdue warnings generated by the background worker.

| Column | Type | Nullable | Default | Constraints & Details |
|---|---|---|---|---|
| `id` | INTEGER | No | Auto-increment | Primary Key |
| `task_id` | INTEGER | No | None | Foreign Key &rarr; `tasks(id)` ON DELETE CASCADE |
| `message` | VARCHAR(500) | No | None | Human-readable notification description |
| `type` | VARCHAR(50) | No | None | Enum: `DUE_SOON`, `OVERDUE` |
| `created_at` | DATETIME | No | CURRENT_TIMESTAMP | Notification creation timestamp |
| `read_at` | DATETIME | Yes | NULL | Timestamp when user marked notification as read |

## 3. Foreign Key & Deletion Behavior

### Cascading Deletions vs. Blocking
In an Agile hierarchy, user stories and tasks cannot meaningfully exist detached from their parent containers:
1. When a **Project** is deleted, all dependent **User Stories** and their subsequent **Tasks** and **Notifications** are deleted automatically via `ON DELETE CASCADE`.
2. When a **User Story** is deleted, all child **Tasks** and their **Notifications** are deleted.
3. When a **Task** is deleted, its **Notifications** are deleted.

### SQLite Foreign Key Enforcement
By default in SQLite, foreign key constraints are disabled for backwards compatibility. In this application, foreign keys and cascading behavior are explicitly activated on every new database connection using the SQLAlchemy `connect` event hook:

```python
@event.listens_for(Engine, "connect")
def set_sqlite_pragma(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.close()
```
This guarantees relational integrity, eliminates orphaned records, and ensures SQLite behaves identically to enterprise relational database management systems.
